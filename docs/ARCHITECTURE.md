# Архитектура и эксплуатация

## Слои

- Workdesk.Server: HTTP, cookie-аутентификация, локальный и командный режимы, ограничение попыток входа, worker.
- Workdesk.Services: проверки доступа, задачи, документы, участники, синхронизация, уведомления и доставка.
- Workdesk.Data: EF Core/SQLite, strongly typed ID, репозитории, UnitOfWork, миграции.
- client: React/TypeScript, MUI, RTK Query из OpenAPI, Zustand для интерфейса, React Hook Form/Zod, Tiptap для визуального редактирования, Markdown как формат хранения, CodeMirror для исходника.

## Авторизация

Локальный режим доверяет владельцу устройства и слушает loopback. Для командного режима: сначала создай аккаунт владельца локально, затем задай `Workdesk__SharedMode=true`, `AllowedHosts` и `Workdesk__AllowedSourceHosts` (список точных хостов API через запятую, при нестандартном порте — с портом). Доступ к API требует HTTPS и входа. По умолчанию доверяются только локальные reverse proxy через стандартные ForwardedHeadersOptions ASP.NET Core. Не включай доверие ко всем входящим X-Forwarded-*.

Права на каждую задачу, документ и историю проверяются сервером. Приглашения хранятся в виде SHA-256 хэша случайного токена, действуют 7 дней и используются один раз. Отзыв членства действует при следующем запросе. Одновременное редактирование защищено версией и ответом 409; автоматического слияния текста нет.

## Данные

Каталог задаёт `WORKDESK_DATA_DIR`, по умолчанию это локальные данные пользователя в папке Workdesk. В каталоге находятся SQLite и ключи cookie. Сохраняй весь каталог при остановленном процессе или используй согласованную резервную копию SQLite. Экспорт JSON содержит доступные текущему пользователю задачи, документы и настройки подключений без токенов. Экспорт не заменяет резервную копию всей базы.

macOS использует связку ключей для токенов. На Linux/Windows при заданном `WORKDESK_MASTER_KEY_FILE` токены шифруются AES-256-GCM с отдельным 32-байтным ключом. В командном режиме на этих ОС ключ обязателен. Без ключа в локальном режиме токены хранятся только в памяти. Ключ хранится отдельно от резервных копий данных.

## Redis и уведомления

Запусти `./scripts/redis-setup.sh`. Он создаёт секреты в `.secrets/` и поднимает Redis в Docker. Папка имеет права 0700; порт 6389 опубликован только на 127.0.0.1. Redis использует AOF, отключённого анонимного пользователя и отдельный ACL для ключей workdesk:*. `start.sh` подхватывает созданный пароль автоматически.

При ручном запуске задай `Workdesk__Redis=127.0.0.1:6389` и `WORKDESK_REDIS_PASSWORD_FILE`. У каждого каталога данных отдельный префикс очереди. В Redis находятся только ID событий, содержимое хранится в базе.

Уникальный индекс базы предотвращает дубли событий. Outbox записывается вместе с импортом. Публикация в Stream идемпотентна через Lua/SET NX. Consumer group подтверждает обработанные записи и подбирает сообщения умерших consumers. Перед внешним вызовом состояние уведомления атомарно меняется на sending. Повторная запись из Stream не вызывает повторной отправки.

После неопределённого сетевого результата состояние становится uncertain и не повторяется автоматически. Это компромисс в пользу отсутствия дублей: отдельное сообщение может потребовать ручной проверки. 429 обрабатывается с retry_after, известные ошибки ограничены пятью попытками. Redis не заменяет базу; потерянная целиком очередь восстанавливается из pending-записей. Удалять отдельные служебные ключи вручную нельзя.

## CI/CD

GitHub Actions проверяет .NET-тесты с Redis, типы и сборку фронтенда, генерацию API, зависимости и секреты, затем Docker-сборку. Официальные actions закреплены по SHA. Тег v* после проверок публикует образ в GHCR с provenance и SBOM. Автоматического развёртывания на корпоративный сервер нет: площадка и её доступы ещё не выбраны.

Контейнер запускается непривилегированным пользователем, данные следует монтировать отдельно. Не открывай личный режим в сеть. Для production нужны HTTPS, резервное копирование, защита хоста и отдельная проверка конфигурации. Текущая SQLite-конфигурация предназначена для одного экземпляра backend с несколькими пользователями; кластер из реплик не поддерживается.
