# Workdesk

Рабочее пространство для задач, документации и команды. GitLab за VPN и GitHub в открытой сети подключаются отдельно; сохранённые материалы остаются доступны при отключённом источнике.

## Что есть в версии 0.4

- Четыре основных раздела: «Сегодня», «Задачи», «Документы» и «Команда». Входящие и архив доступны во вкладках задач.
- Документы: визуальный редактор, меню блоков по `/`, таблицы и чек-листы, дерево страниц, история и шаблоны. Создание документа прямо с экрана «Сегодня».
- Markdown остаётся форматом хранения; исходник открывается по кнопке `<>`. Документы с HTML и сносками открываются в исходнике, чтобы сохранить эти элементы.
- Ссылки `[[название]]`, постоянные ссылки на документы, обратные ссылки и поиск `Ctrl/Cmd+K`.
- Импорт `.md` и экспорт ZIP со связями для Obsidian. Личные документы и общие пространства.
- Команды: единый диалог приглашений, выбор прав, копирование ссылки и подтверждение удаления участника. Приглашение по логину или одноразовой ссылке с регистрацией. Отправка писем пока не реализована.
- Доска с ближайшим шагом на карточке, переносом через меню и перетаскиванием. В задаче: описание, рабочие заметки и связанные документы с обратным переходом.
- Личная и общая доски, назначение участника, сводка по milestone и выгрузка итогов в Markdown.
- Несколько GitLab/GitHub, выбранные проекты, импорт назначенных задач, уведомления о новых задачах и комментариях в связанных с пользователем MR/PR.
- Личные уведомления, Telegram, outbox в SQLite и Redis Streams с защитой от повторной доставки.
- Светлая, тёмная и системная темы.

ИИ пока не подключён. Совместное редактирование использует версии и обнаружение конфликтов; одновременного набора текста с курсорами участников нет.

## Локальный запуск

Нужны .NET SDK 10, Node.js 24 и Corepack/Yarn 4. Docker нужен для Redis или контейнерного запуска.

```bash
./scripts/redis-setup.sh
./start.sh
```

Открой <http://127.0.0.1:5284>. `start.sh` устанавливает зависимости, собирает приложение и подключает подготовленный Redis. Без Redis доступен локальный режим с очередью в базе.

В macOS токены хранятся в связке ключей. На других ОС настрой `WORKDESK_MASTER_KEY_FILE`: бинарный файл из 32 случайных байт вне каталога данных. Без него локальный режим хранит токены только до перезапуска. Каталог данных задаёт `WORKDESK_DATA_DIR`; по умолчанию это системная папка локальных данных пользователя, каталог `Workdesk`.

## Подключения и VPN

В разделе «Подключения» создай отдельную запись для каждого сервера. Примеры адресов: `https://gitlab.example.org/api/v4/`, `https://api.github.com/`, `https://github.example.org/api/v3/`.

Используй токен с доступом только к нужным проектам и минимальными правами чтения. В поле проектов укажи GitLab ID/пути или GitHub `owner/repo`, по одному в строке. Для комментариев MR/PR список проектов обязателен. Workdesk не меняет удалённые задачи и не коммитит код.

VPN должен быть доступен процессу backend. Отметка VPN показывает требование к сети и не управляет VPN-клиентом. Каждый источник синхронизируется отдельно примерно раз в пять минут; есть ручной запуск. Первая загрузка создаёт базовое состояние без пачки старых уведомлений. После изменения списка проектов базовое состояние строится заново; уже импортированные задачи сохраняются.

В Telegram добавь токен бота и `chat_id` в разделе «Уведомления». Текст события включает название и ссылку; содержимое документов и полные комментарии не отправляются. При неоднозначном сетевом результате доставка получает статус «Требует проверки» без автоматического повтора.

## Команда и сервер

Сначала создай учётную запись владельца в локальном режиме, затем пространство в разделе «Команда». Участник по логину принимает приглашение в своём аккаунте. Новый участник открывает ссылку, регистрируется и сразу получает указанную роль. Ссылка действует семь дней и используется один раз. Отправлять ссылку нужно самостоятельно.

Для работы с других устройств нужен общий сервер. Локальный режим доверяет владельцу компьютера и не предназначен для сетевого доступа. В командном режиме обязательны:

- `Workdesk__SharedMode=true`, HTTPS и учётная запись владельца, созданная заранее.
- `AllowedHosts` с именами приложения через `;` и `Workdesk__AllowedSourceHosts` с точными хостами API через `,`.
- Защищённый ключ для токенов на Linux/Windows, резервное копирование и доступ сервера к корпоративной сети.

Дополнительные доверенные IP reverse proxy задаются через `Workdesk__TrustedProxies`. По умолчанию доверяется локальный proxy. Сам backend оставляй за firewall и proxy.

```bash
./scripts/redis-setup.sh
docker compose --profile app up -d --build
```

Контейнер использует собственный volume и не переносит данные локального запуска автоматически. Сначала создай владельца через loopback, затем включи командный режим переменной `WORKDESK_SHARED_MODE=true`, настрой домен (`WORKDESK_ALLOWED_HOSTS`), хосты API (`WORKDESK_SOURCE_HOSTS`), доверенный proxy и HTTPS. Пример: [deploy/.env.example](deploy/.env.example).

## Разработка и проверки

```bash
dotnet test
cd client
corepack yarn install --immutable
corepack yarn dev
corepack yarn build
```

Фронтенд на `5173` проксирует API на `5284`. `WORKDESK_BACKEND_URL` меняет адрес backend для Vite. `corepack yarn generate-api` обновляет RTK Query из запущенного Swagger; `WORKDESK_SCHEMA_URL` задаёт альтернативный адрес схемы. Файлы `client/src/api/autogen` не редактируются вручную.

Для интеграционного теста Redis задай `WORKDESK_TEST_REDIS` и при необходимости `WORKDESK_TEST_REDIS_PASSWORD_FILE`. Без адреса этот тест пропускается.

GitHub Actions собирает backend, запускает тесты с Redis, проверяет генерацию API, зависимости, секреты и контейнер. Теги `v*` запускают проверку и публикацию контейнера в `ghcr.io/akisomadinov/workdesk:<tag>` с SBOM и provenance. Развёртывание на сервер настраивается отдельно.

## Данные и ограничения

Перед обновлением сделай согласованную резервную копию SQLite и ключей. Для простой полной копии останови приложение и сохрани весь каталог данных; ключ шифрования токенов держи отдельно. JSON/Markdown-экспорт не заменяет полную резервную копию. Токены в экспорт не попадают. Черновики редактора сохраняются в браузере: используй отдельный профиль на общем компьютере.

Текущий сервер рассчитан на один экземпляр backend и небольшую команду, использует SQLite. Нет SSO, MFA, сброса пароля по почте, файловых вложений и webhook-синхронизации. Корпоративные инсталляции GitLab/GitHub требуют проверки совместимости и прав токена. Внешний аудит безопасности не проводился.
