# Workdesk

Рабочее пространство для задач, документации и команды. GitLab за VPN и GitHub в открытой сети подключаются отдельно; сохранённые материалы остаются доступны при отключённом источнике.

## Что есть в версии 0.4

- «Сегодня»: первая задача с причиной выбора, просроченный план, ожидания без даты и быстрый перенос на другой день.
- Удаление задач и документов с подтверждением и восстановлением из корзины.
- Четыре основных раздела: «Сегодня», «Задачи», «Документы» и «Команда». Входящие и архив доступны во вкладках задач.
- Документы: визуальный редактор, меню блоков по `/`, таблицы и чек-листы, дерево страниц, история и шаблоны. Отдельный раздел с действиями в списке и меню по правой кнопке мыши.
- Markdown остаётся форматом хранения; исходник открывается по кнопке `<>`. Документы с HTML и сносками открываются в исходнике, чтобы сохранить эти элементы.
- Ссылки `[[название]]`, постоянные ссылки на документы, обратные ссылки и поиск `Ctrl/Cmd+K`.
- Импорт `.md` и экспорт ZIP со связями для Obsidian. Личные документы и общие пространства.
- Команды: единый диалог приглашений, выбор прав, копирование ссылки и подтверждение удаления участника. Приглашение по логину или одноразовой ссылке с регистрацией. Отправка писем пока не реализована.
- Доска с ближайшим шагом на карточке, переносом через меню и перетаскиванием. В задаче: описание, рабочие заметки и связанные документы с обратным переходом.
- Личная и общая доски, назначение участника, сводка по milestone и выгрузка итогов в Markdown.
- Несколько GitLab/GitHub, выбранные проекты, импорт назначенных задач, уведомления о новых задачах и комментариях в связанных с пользователем MR/PR.
- Отдельный раздел «Мои MR»: свои запросы, назначенное ревью, сохранённая история комментариев, непрочитанные и настройка уведомлений для каждого MR/PR.
- Личные уведомления, Telegram, outbox в SQLite и Redis Streams с защитой от повторной доставки.
- Светлая, тёмная и системная темы.

ИИ пока не подключён. Совместное редактирование использует версии и обнаружение конфликтов; одновременного набора текста с курсорами участников нет.

## Локальный запуск

Нужны .NET SDK 10, Node.js 24 и Corepack/Yarn 4. Docker нужен для Redis или контейнерного запуска.

```bash
./scripts/redis-setup.sh
./start.sh
```

Открой <http://127.0.0.1:5284>. `start.sh` устанавливает зависимости, собирает приложение и подключает подготовленный Redis. Без Redis доступен локальный режим с очередью в базе.

В macOS токены хранятся в связке ключей. На других ОС настрой `WORKDESK_MASTER_KEY_FILE`: бинарный файл из 32 случайных байт вне каталога данных. Без него локальный режим хранит токены только до перезапуска. Каталог данных задаёт `WORKDESK_DATA_DIR`; по умолчанию это системная папка локальных данных пользователя, каталог `Workdesk`.

## Подключения и VPN

Нажми на аккаунт с шестерёнкой внизу панели и открой «Подключения» в настройках. Создай отдельную запись для каждого сервера. Примеры адресов: `https://gitlab.example.org/api/v4/`, `https://api.github.com/`, `https://github.example.org/api/v3/`.

Используй токен с доступом только к нужным проектам и минимальными правами чтения. В поле проектов укажи GitLab ID/пути или GitHub `owner/repo`, по одному в строке. Для комментариев MR/PR список проектов обязателен. Workdesk не меняет удалённые задачи и не коммитит код.

VPN должен быть доступен процессу backend. Отметка VPN показывает требование к сети и не управляет VPN-клиентом. Каждый источник синхронизируется отдельно примерно раз в пять минут; есть ручной запуск. Первая загрузка создаёт базовое состояние без пачки старых уведомлений. После изменения списка проектов базовое состояние строится заново; уже импортированные задачи сохраняются.

При первом импорте GitLab метки определяют колонку: `backlog` → «Входящие», `ToDo` и `bugs` → «Запланировано», `InProgress` → «В работе», `Test` и `DevDone` → «Ожидаю», `TestDone` → «Готово». `DevDone` означает отправку MR на ревью, `Test` — ожидание результата тестирования; причина ожидания указывается в карточке. Регистр не важен. Закрытые задачи сразу попадают в «Готово». Если меток несколько, завершение важнее тестирования, тестирование важнее ревью, ревью важнее работы, работа важнее планирования. Неизвестные метки оставляют задачу во «Входящих»; метки приоритета вроде «Баг B» не считаются `bugs`. Повторная синхронизация сохраняет личную колонку, заметки и план работы.

В подключении можно включить отслеживание MR/PR. «Мои MR» показывает запросы выбранных проектов, где пользователь — автор, исполнитель или ревьюер. Первая загрузка сохраняет открытые запросы и их комментарии без уведомлений о старой истории; последующие загрузки обновляют состояния, включая слияние и закрытие. Для MR используется отдельная точка синхронизации. Если VPN недоступен, сохранённые обсуждения остаются доступны. Разовый импорт не заменяет токен для фонового обновления.

Колокольчик у MR отключает будущие уведомления в приложении и Telegram; новые комментарии продолжают сохраняться. Непрочитанные отмечаются отдельно, кнопка «Прочитано» действует на показанную страницу обсуждения и связанные уведомления. Свои и системные комментарии не вызывают оповещения. Комментарии GitHub включают обсуждение PR, замечания к строкам и текст отправленных ревью. Отправка ответа выполняется в исходном трекере. MR и их комментарии личные и не зависят от выбранного командного пространства. JSON-экспорт задач и документов пока не включает кэш MR; полная копия базы SQLite включает его.

Интеграция читает [API merge requests GitLab](https://docs.gitlab.com/api/merge_requests/) и [API комментариев GitLab](https://docs.gitlab.com/api/notes/).

Замечания к коду показывают путь файла, номера строк до и после изменения, выделенный фрагмент diff и версию коммита. GitLab Discussions связывается с точной сохранённой версией diff; GitHub использует `diff_hunk` комментария. Ответы в обсуждении GitLab наследуют его контекст. Если исторический diff недоступен, приложение показывает место замечания без подстановки текущего кода. Сохранённый фрагмент доступен без VPN; код не включается в Telegram-сообщение.

Для Telegram добавь токен бота и `chat_id` в «Настройки → Уведомления». Колокольчик открывает ленту событий. Текст события включает название и ссылку; содержимое документов и полные комментарии не отправляются. При неоднозначном сетевом результате доставка получает статус «Требует проверки» без автоматического повтора.

Для команды можно настроить общего бота: положи токен в защищённый файл и задай серверу `WORKDESK_TELEGRAM_BOT_TOKEN_FILE`. По умолчанию проверяется `secrets/telegram-bot-token` внутри каталога данных Workdesk. Файл должен быть доступен только владельцу процесса (на Unix `chmod 600`); в контейнере подключай его как read-only secret. Токен не передаётся браузеру. Один бот должен обслуживаться одним сервером Workdesk, без другого получателя `getUpdates` или webhook.

В настройках Telegram нажми «Подключить Telegram», открой одноразовую ссылку и нажми Start. **Start только предлагает аккаунт для привязки**: вернись в Workdesk, проверь имя, `@username` и числовой ID, затем нажми «Подтвердить этот аккаунт». Подтвердить привязку можно только из того же аккаунта Workdesk, в котором создана ссылка. Если аккаунт чужой, отмени запрос. Первый полученный аккаунт закрепляется за запросом; повторный Start не может незаметно подменить его. Ссылка содержит 192 случайных бита, действует 10 минут и хранится только в виде SHA-256. Отмена, истечение срока и новая ссылка делают старое подтверждение недействительным. Группы не привязываются. Смена чата отменяет ещё не отправленные уведомления; отмена нового запроса сохраняет прежнее подключение. Для работы серверу нужен доступ к `api.telegram.org`; HTTPS-прокси можно задать стандартной переменной `HTTPS_PROXY`.

Для отдельного маршрута Telegram задай `WORKDESK_TELEGRAM_PROXIES`: до четырёх URL `socks5://host:port`, `http://host:port` или `https://host:port`, через запятую, в порядке приоритета. Альтернатива — файл `secrets/telegram-proxies` в каталоге данных, по одному URL в строке, или путь в `WORKDESK_TELEGRAM_PROXIES_FILE`. Прокси с логином и паролем в URL не поддерживаются; для локальных SSH-туннелей привязывай SOCKS-порт к `127.0.0.1`.

Этот список применяется только к Telegram, включая чтение команд и отправку уведомлений. Перед выбором выполняется запрос без токена, проверяющий соединение, DNS и TLS; результат кешируется на 15 секунд, недоступный маршрут проверяется снова через 30 секунд. При отказе первого используется следующий. Если недоступны все, запрос боту не отправляется и доставка может быть повторена позже. После неоднозначной ошибки уже начатой отправки сообщение не пересылается через другой прокси: остаётся статус «Требует проверки», чтобы не создать дубликат. Без списка прокси сохраняется обычное сетевое поведение приложения. SSH-туннели запускаются отдельно на машине сервера; параметры личных серверов и ключи не входят в репозиторий.

## Команда и сервер

Без аккаунта приложение работает локально на этом компьютере. После создания аккаунта личные данные требуют входа, в том числе в локальном режиме. Выход находится в меню аккаунта справа в шапке и закрывает доступ до повторного входа. Пространство переключается слева в шапке; рядом можно свернуть панель. Тема выбирается через иконку солнца/луны и сохраняется в браузере.

В разделе «Команда» создай аккаунт, затем команду. Кнопка «Пригласить» открывает выбор способа и прав: читатель просматривает материалы, редактор может создавать, изменять и удалять их. По логину (можно с `@`) приглашение появляется у получателя в Workdesk. По ссылке можно войти или зарегистрироваться и сразу получить выбранную роль. Ссылка действует семь дней и используется один раз. Отправлять ссылку нужно самостоятельно.

Переключатель пространства в шапке общий для команды, доски и документов. «Личное» содержит личные материалы и назначенные тебе задачи; выбор команды открывает её общие материалы. Выбор сохраняется в текущей вкладке после перезагрузки и сбрасывается при смене аккаунта. Владелец меняет права нажатием на роль участника; удаление требует подтверждения.

Для работы с других устройств нужен общий сервер. Локальный режим доверяет владельцу компьютера и не предназначен для сетевого доступа. В командном режиме обязательны:

- `Workdesk__SharedMode=true`, HTTPS и учётная запись владельца, созданная заранее.
- `AllowedHosts` с именами приложения через `;` и `Workdesk__AllowedSourceHosts` с точными хостами API через `,`.
- Защищённый ключ для токенов на Linux/Windows, резервное копирование и доступ сервера к корпоративной сети.

Дополнительные доверенные IP reverse proxy задаются через `Workdesk__TrustedProxies`. По умолчанию доверяется локальный proxy. Сам backend оставляй за firewall и proxy.

```bash
./scripts/redis-setup.sh
docker compose --profile app up -d --build
```

Контейнер использует собственный volume и не переносит данные локального запуска автоматически. Сначала создай владельца через loopback, затем включи командный режим переменной `WORKDESK_SHARED_MODE=true`, настрой домен (`WORKDESK_ALLOWED_HOSTS`), хосты API (`WORKDESK_SOURCE_HOSTS`), доверенный proxy и HTTPS. Пример: [deploy/.env.example](deploy/.env.example).

## Разработка и проверки

```bash
dotnet test
cd client
corepack yarn install --immutable
corepack yarn dev
corepack yarn build
```

Фронтенд на `5173` проксирует API на `5284`. `WORKDESK_BACKEND_URL` меняет адрес backend для Vite. `corepack yarn generate-api` обновляет RTK Query из запущенного Swagger; `WORKDESK_SCHEMA_URL` задаёт альтернативный адрес схемы. Файлы `client/src/api/autogen` не редактируются вручную.

Для интеграционного теста Redis задай `WORKDESK_TEST_REDIS` и при необходимости `WORKDESK_TEST_REDIS_PASSWORD_FILE`. Без адреса этот тест пропускается.

GitHub Actions собирает backend, запускает тесты с Redis, проверяет генерацию API, зависимости, секреты и контейнер. Теги `v*` запускают проверку и публикацию контейнера в `ghcr.io/akisomadinov/workdesk:<tag>` с SBOM и provenance. Развёртывание на сервер настраивается отдельно.

## Данные и ограничения

Перед обновлением сделай согласованную резервную копию SQLite и ключей. Для простой полной копии останови приложение и сохрани весь каталог данных; ключ шифрования токенов держи отдельно. JSON/Markdown-экспорт не заменяет полную резервную копию. Токены в экспорт не попадают. Черновики редактора сохраняются в браузере: используй отдельный профиль на общем компьютере.

Текущий сервер рассчитан на один экземпляр backend и небольшую команду, использует SQLite. Нет SSO, MFA, сброса пароля по почте, файловых вложений и webhook-синхронизации. Корпоративные инсталляции GitLab/GitHub требуют проверки совместимости и прав токена. Внешний аудит безопасности не проводился.
